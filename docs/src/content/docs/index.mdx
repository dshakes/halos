## How it works

Your **platform team** keeps one git repo of Halos YAML: which CLI versions, models, permissions, MCP servers and hooks each ring of developers gets. Every change is a pull request that `halo` validates, plans and evals; a human merges it, and Halos ships a signed release ring by ring to every machine and gateway. **Developers install nothing new and never touch the repo**: they keep running `claude`, `codex` or `gemini`.

## 60-second start

```console
$ git clone https://github.com/dshakes/halos && cd halos && make build && export PATH=$PWD/bin:$PATH
$ mkdir my-policy && cd my-policy
$ halo init                                       # one halos.yaml: the whole policy
create halos.yaml
$ halo validate
OK: policy valid (0 warnings)
$ halo whoami --user you@example.com              # which ring and profile you'd get
ring     ring3-ga
$ halo render --ring ring3-ga --out rendered      # exactly what a developer's machine gets
write rendered/Library/Application Support/ClaudeCode/managed-settings.json
```

Or skip all of it: `make demo` runs the whole stack locally, and the Codespaces badge above runs it in your browser. Homebrew, the packages and the installers switch on with the first tagged release.

Then take [your first 10 minutes](/halos/tutorials/first-10-minutes/), or the [quickstart](/halos/getting-started/quickstart/). Pre-release (`v1alpha1`), Apache-2.0, self-hosted; anything not yet run against a real third-party system is marked **UNVERIFIED** in the docs.

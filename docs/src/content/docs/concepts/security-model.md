| Boundary | Threat | Control |
|---|---|---|
| Registry to `halod` | Tampered release; replay of an older signed release; frozen registry; release built for another org or ring | Signed ring pointer `{org, ring, digest, seq, expiry}`; release signature; ([ADR-0005](/halos/adr/0005-signed-oci-bundles/), [ADR-0008](/halos/adr/0008-signed-ring-pointers-and-verified-artifacts/)) |
| Vendor download to `halod` | Compromised or swapped CLI binary; install script run as root | Hash-pinned artifacts from the signed manifest; no `curl \| bash`; npm `--ignore-scripts` |
| Manifest to root filesystem | Signing key alone writing arbitrary files as root | Per-harness path allowlist, 0644 mode ceiling, root-ownership and symlink checks |
| Client to gateway | Client claims a ring, variant or identity; unknown or batch model endpoints; other models | OIDC JWT verified at the gateway; every inbound `x-halo-*` stripped; fail-closed model allowlist |
| Policy to harness | Dangerous permission modes, non-allowlisted overrides, secrets in bundles | Go guardrails at validate and again at release, plus a rendered-output backstop |
| Workspace to internet | Exfiltration by agent | Egress firewall to `egress.allowedDomains` plus the harness sandbox |
| Laptop enrollment | Stolen or replayed enrollment token | Single-use, short TTL, stored only as SHA-256; device token stored only as SHA-256 and revocable |
| Shadow store | Prompt leakage; shadow token aiming replays at arbitrary URLs | Upstreams resolved from policy; AES-256-GCM at rest; retention; budget |
| Signer to registry | A registry serving an old signed pointer that `refresh` or `promote` would re-sign into a fresh one | Signer state file, promote from the source ring's signed pointer, expired pointers refused ([below](#signer-continuity)) |
| Developer machines to the collector | Forged metrics that trip, promote or hide an experiment | Up to three receivers (CLI, gateway, optional eval); only the authenticated gateway receiver may drive a kill ([below](#evidence-trust)) |
| `halo-server` to gateway | Forged, stale or replayed kill list; a stolen release key forging kills; an attacker on the path un-killing an experiment | Kill list signed with a dedicated ed25519 key; gateway token; freshness and strictly-newer checks ([below](#kill-switch)) |
| Console and API to privileged actions | One over-broad admin group; a new route reachable by everyone; silent or rewritten history of who killed, revoked or changed what | Five roles from IdP groups, one deny-by-default route table, audited denials ([below](#console-roles)); hash-chained audit log ([below](#audit-log)) |
| IdP to `halo-server` (SCIM) | A departed user keeping sessions, devices or cohort; a session or leaked gateway token provisioning users; groups injected by a client | Dedicated SCIM token stored as SHA-256; deprovisioning revokes at once; directory groups keyed by the verified subject ([below](#scim-provisioning)) |
| `halo-proxy` to Bedrock | Client credentials reaching AWS; unsigned requests | Client auth stripped, request SigV4-signed with the gateway's own AWS identity; no credentials means 502, never unsigned ([below](#bedrock-credentials)) |
| CI / cloud workload to gateway | A long-lived provider key in CI; another repository or branch posing as a trusted pipeline; a replayed or forged CI token | Federated OIDC token exchanged at `halo-server` for a 15-minute (at most 1 hour) credential signed with a dedicated ed25519 key; per-issuer claim rules; jti replay cache ([below](#workload-credentials)) |

## Signing

Releases are OCI artifacts signed with ed25519. The primary signer must be ed25519 because `halod` verifies only ed25519 and never shells out to cosign as root. cosign (key, KMS URI or keyless) can be added as a co-signature (`--cosign-key`, `--cosign-keyless`); keyless uploads the release digest to the public Rekor transparency log.

Protect the signing key: anyone who can sign can ship hooks to every developer. Use a CI-only or KMS-backed key, and require PR review on ring changes. See [production deployment](/halos/guides/production-deployment/) for rotation.

### Signed ring pointers (TUF-lite)

A ring tag alone is unauthenticated: whoever controls the registry could retag it to an older signed release or one built for another ring. So each ring has a separately signed pointer with `org`, `ring`, `digest`, `seq`, `issuedAt` and `expiresAt`. `halod` trusts the pointer, checks the fields against its config, refuses a lower `seq` than it last applied, refuses an expired pointer (7-day TTL), and only then fetches the release the pointer names by content digest, never by a mutable tag.

Consequences: a compromised registry cannot roll a ring back to an older signed release, cannot serve a release for another org or ring, and cannot freeze clients indefinitely without them noticing (they stop updating and warn after 7 days). Rollback is a new pointer with a higher `seq`. **Pointers must be refreshed on a schedule** (`halo release refresh`, daily) or every client stops updating after seven days; `halod` warns when fewer than 24 hours remain.

This is not full TUF: there is no root key rotation protocol, threshold signing or delegated roles. A key compromise is handled by rotating the key in every `halod` config (see [production deployment](/halos/guides/production-deployment/)).

### Signer continuity

`halod` checks pointers it reads. The signer needs the same discipline, because a registry can serve an old but validly signed pointer, and a signer that refreshes "what the registry serves" would re-issue it with a higher `seq` and a fresh expiry. The release commands close that:

- **Promote follows the source ring's signed pointer.** `halo release promote --from-ring A --to-ring B` reads A's signed pointer (signature, ring, org, expiry, continuity), fetches the release it names and checks its digest against the pointer. The `ring-A` tag, which is unauthenticated, is never used as the source.
- **Rollback needs a matching version.** `halo rollback --to <version>` resolves tag `v<version>` and refuses the release unless its **signed manifest** carries that version, so a retagged `v` tag cannot redirect it. `--to sha256:<manifest digest>` is the OCI manifest digest and is content-addressed.
- **Refresh refuses expired pointers.** An expired pointer cannot be told apart from a replayed one. Recover explicitly with `halo rollback --to <version>`.
- **Signer state file.** The last pointer written per registry repo and ring (`seq`, `digest`, `issuedAt`) is kept in `$XDG_STATE_HOME/halos/pointers.json` (`--state-file`). A served pointer with a lower `seq`, the same `seq` and another digest, or no pointer where one was written is refused. New `seq = max(served + 1, recorded + 1, unix now)`.
- **`--expect-digest sha256:<release digest>`** on `refresh`, `promote` and `rollback` refuses unless the release involved is exactly that one: the check that works without state.
- **Every signature is announced.** Before signing, the CLI prints `Signing ring X → version V (digest D, seq S)` to stderr.

Limit: **stateless CI has no state file**, and a signer with no record for a ring refuses to re-sign a pointer the registry already serves unless you confirm it with `--expect-digest` (the served release digest) or `--adopt-existing` (use it only on a first run or after a cache eviction: it trusts what the registry serves, so that run has no replay protection). Cache `pointers.json` between runs ([production deployment](/halos/guides/production-deployment/#replay-protection-the-signer-state-file)). The file has one writer; an unparseable file blocks signing rather than disabling the check.

## Evidence trust

Experiments decide rollouts, so telemetry is an attack surface. Developer machines must reach the collector, so the CLI receiver is client-controlled. The collector (`halo telemetry collector-config`) therefore has two receivers by default, plus an optional third: the CLI receiver (4317/4318) drops every `halo.gateway.*` metric, stamps `halo.source=cli`, caps requests at 4 MiB and can require per-device bearer tokens (`--cli-token-file`); the gateway receiver (4319) requires `HALO_OTLP_GATEWAY_TOKEN`, which `halo-proxy` presents (`--telemetry-token-file`), and stamps `halo.source=gateway`. The optional eval receiver (`--eval-receiver`, 4320) accepts only `halo.eval.*` metrics, stamps `halo.source=eval` and requires its own token, `HALO_OTLP_EVAL_TOKEN` (never the gateway token), so `halo eval online` can publish without gateway credentials; nothing auto-kills on eval-sourced rows. Analysis trusts gateway rows only with that stamp, and the controller **auto-kills only on gateway-sourced evidence**; a CLI-sourced rollback still opens the pause PR and notifies. Units are `HMAC(salt, verified subject)`, so a client cannot choose or inflate its own unit. Details: [evidence plane](/halos/concepts/evidence-plane/#evidence-trust).

## Kill switch

The kill switch lets `halo-server` (the controller on a rollback verdict, or an operator) switch an experiment off at the gateways in seconds. Because it can change live routing without a merge, it has its own trust chain:

- **Separate key.** The kill list is signed with its own ed25519 key (`halo keys generate --name killswitch`, private half in `halo-server --killswitch-key-file`). It is **not** the release key. A stolen kill key can kill experiments (routing everyone to control) but cannot sign a release or a ring pointer; a stolen release key cannot forge a kill list. The signature covers a domain prefix (`halo-killswitch-v1\n`) plus the payload, so it cannot be confused with any other signature.
- **Gateway token.** Gateways fetch the list with a bearer token (`--gateway-token-file`, or a dedicated `--gateway-killswitch-token-file`), compared in constant time, with failed attempts rate-limited per client IP. The endpoint returns 404 unless both the key and the token are configured. The token gates who can read the list, the signature gates what a gateway believes. `halo-server` refuses to start with any gateway token (shared or per capability) shorter than 32 characters or under 128 bits of estimated entropy (length times log2 of its distinct characters); generate one with `openssl rand -hex 32`.
- **Freshness.** A list is rejected if its `issuedAt` is more than 10 minutes old or more than 1 minute in the future.
- **Replay.** A list is accepted only if its `issuedAt` is strictly newer than the list the gateway already holds, so replaying an older envelope cannot undo a kill.
- **Fail toward keeping kills.** If the fetch or verification fails, the gateway keeps the last accepted list. If it never accepted one, it kills nothing and the policy snapshot decides. Kills do not expire.
- **Operator actions are audited, fail-closed.** Kill and unkill (by an operator or admin, or by the controller as `halo-controller`) write `experiment.kill` and `experiment.unkill` (`toggle.kill` and `toggle.unkill` for feature toggles) audit entries with the reason ([audit log](#audit-log)). A kill needs a reason (HTTP 422 without one).
- **No key, no kill.** Without `--killswitch-key-file` (which requires `--data-dir` and `--gateway-token-file`) the server serves no list, answers 501 to kill and unkill, and `GET /api/v1/capabilities` reports `killSwitch: false`. The in-process controller then does not pretend: it reports the rollback as not enforced and asks humans to merge the pause PR urgently.
- **The controller holds killed experiments.** A running experiment that is already killed is not evaluated (its evidence is all control); humans are told once to unkill before resuming.
- **TLS for the token.** Gateways refuse plain `http://` to a non-loopback kill URL, since the bearer token would travel in the clear, unless `killSwitch.allowInsecureInCluster` (`halo-kong`: `killswitch_allow_insecure_in_cluster`) is set for a trusted in-cluster URL. A misconfigured `halo-kong` still serves traffic but logs at ERROR and adds `x-halo-killswitch: misconfigured` to the upstream request.
- **Notification webhooks are signed and timestamped.** The controller's generic webhook carries `X-Halo-Timestamp` and `X-Halo-Signature: sha256=<hex>`, an HMAC-SHA256 over `timestamp + "." + body` under a shared secret. Receivers must verify it and reject timestamps more than 5 minutes off, which stops replay of a captured request ([snippets](/halos/reference/binaries/#verifying-the-webhook-signature)). Delivery is retried per channel on later ticks. Slack uses its own incoming-webhook URL, which is itself a secret.

Limits: a kill affects gateways (routing and mirroring). It reaches client-axis variants on machines only where `halod` has `killSwitch` configured (portal enrollment sets it when `halo-server` has a kill key); otherwise those revert on pause and republish ([details](/halos/concepts/experiments/#limits-the-client-axis)). If `halo-server` is down when a kill is issued, nothing is killed until it is back. Decision record: [ADR-0009](/halos/adr/0009-signed-kill-switch/).

## Console roles

`halo-server` grants authority by role, not by one admin flag ([ADR-0015](/halos/adr/0015-rbac-roles-for-halo-server/)). Policy maps IdP groups to roles in `identity.roles`; `identity.adminGroups` still grants `admin`.

| Role | May |
|---|---|
| `viewer` | Read fleet, devices, releases, rollouts, experiments, toggles, the kill list and policy |
| `operator` | Viewer, plus kill and unkill experiments and toggles, and open experiment status PRs |
| `approver` | Viewer, plus approve and deny access requests |
| `auditor` | Read and export the audit log, nothing else |
| `admin` | Everything, including device and session revocation and toggle proposals |

- **One table, deny by default.** Every cookie-authenticated route is in `routePerms` (`internal/server/rbac.go`) with the one permission it needs. A route registered without an entry answers 403 to everyone, admins included, and a test walking the server's routes fails until the entry is added.
- **Roles come from current policy.** They are recomputed from the session's groups on every request, never read from the cookie, so removing a group from a role takes effect at once. A misspelled role name in policy is a load error.
- **Denials are audited.** A 403 for a missing permission appends `authz.deny` with the user, path, route, needed permission and the user's roles.
- **The console only hides.** `/api/v1/me` and `/api/v1/capabilities` report the caller's roles and permissions so the console can hide what it may not do; the server enforces either way.

## Audit log

Privileged actions (login, logout, authorization denials, device enroll and revoke, session revoke, access-request decisions, experiment status PRs, kill and unkill) append to `audit.jsonl` in `--data-dir`. Each entry carries `seq`, `prev` (the previous entry's hash) and its own `hash` over every other field. With rotation on, full segments become `audit-<seq>.jsonl` and the chain runs on across them: a segment's first `prev` is the previous segment's last `hash`. `GET /api/v1/audit` verifies the whole chain, every segment, and returns `verified` plus a `head` hash; `halo audit verify` does the same offline. Editing, reordering or removing any entry except the newest breaks the chain from that point on, and the console shows it.

Appends are fsynced before the action is acknowledged, and **privileged actions fail closed**: kill and unkill, device enrollment, session and device revocation and experiment-status PRs return HTTP 500 if the append fails. A kill whose audit append fails stays applied (fail safe), a failed unkill is reverted, and a revocation stays in force; the audit gap is what the error reports. `halo controller run` appends through the same chain, so it is a **single writer**: never run it against a data dir a live `halo-server` is writing.

**Limit: tail truncation is undetectable from the log alone.** Dropping the newest entries leaves a chain that still verifies. [SIEM export](/halos/guides/siem-export/) is the external copy that closes this: every entry, with `seq`, `prev` and `hash`, leaves the host at least once and in order, so the SIEM holds entries a truncated log lacks. The forwarder ships only entries that continue the chain it already shipped (same `seq + 1`, matching `prev` and hash) and halts on the first that does not, so an edit made on disk after an entry was exported is never exported as if it were the original. Export never delays or fails an action; credentials are environment or file references, never in the config or logs ([ADR-0016](/halos/adr/0016-audit-export-to-siem/)). The log is also only as trustworthy as the host's file permissions: someone who can rewrite the file can recompute every hash. Without `--data-dir` the log lives in memory and is lost on restart.

## SCIM provisioning

`halo-server` is a SCIM 2.0 service provider at `/scim/v2` for Okta and Entra ID ([ADR-0022](/halos/adr/0022-scim-provisioning/), [setup](/halos/guides/scim-provisioning/)).

- **Own credential.** The IdP authenticates with a dedicated bearer token. The server holds only its SHA-256 (`--scim-token-sha256-file`; two hashes during a rotation), compares in constant time against each, and rate-limits failures per client IP in a budget of its own. Session cookies, the gateway token and the fleet token are never accepted on `/scim/v2`.
- **Failed-auth budgets are per endpoint class.** Token exchange, SCIM, gateway tokens, device tokens and enrollment, and OIDC callbacks each have their own per-IP budget, so garbage sent to a public endpoint from an IP a gateway shares cannot lock the gateway out of its directory, posture, budget or kill-list endpoints. A valid gateway token is accepted even from a blocked IP; gateway tokens have at least 32 characters and 128 bits of estimated entropy (enforced at startup), so the oracle this gives a blocked guesser does not make guessing feasible.
- **Deprovisioning is immediate.** Deactivating, deleting or renaming a user bumps their session epoch (every console session dies), revokes every device token bound to them and drops their unconsumed enrollment tokens before the change is stored. A user id is compared and keyed in one canonical form everywhere (lowercased, surrounding space trimmed: session epochs, devices, enrollments, posture, directory lookups, access-request self-approval, the whoami self check and per-user budget counters), so an IdP that provisions `Alice@Corp.com` still ends the sessions of `alice@corp.com`, and cannot approve its own request, or get a fresh budget, under another case. Only real case pairs fold: a lookalike such as the Kelvin sign (`\u212A`) or a dotted capital I stays a different user, where `strings.ToLower` would have made `\u212Aelly` share kelly's sessions and budget. A deactivated user is refused at login, on console requests and on device endpoints.
- **Authoritative groups never come from the client.** With `--scim-authoritative`, users the directory does not list as active are refused, and admin rights, ring resolution and toggle targeting use the directory's groups. Gateways with `directory.url` replace a verified caller's groups with the directory's and refuse (403, in the caller's protocol) a verified caller the directory does not list as active, rather than demoting them to an anonymous caller who would skip the posture gate and per-user budgets; the lookup key is the verified subject. Workload credentials are not in SCIM and skip the lookup.
- **An outage never makes a caller anonymous.** When the directory cannot be asked past `grace` (or its config is invalid), `directory.failMode: open` (the default; `directory_fail_mode` on `halo-kong`) keeps the verified subject with no groups: default routing and no experiments, with the posture gate and per-user budgets still applied to that subject. `closed` answers 503 in the caller's protocol. Fail open is for an outage only: a transport error or a 5xx. Any other answer from `halo-server` that is not 200 (a subject it will not look up, a rejected token) refuses the caller as not provisioned, and a caller whose last cached entry was inactive stays refused however long the outage lasts. `halo-server` answers an oversized subject (over 256 characters) as inactive, not with an error.
- **`workload:` is reserved.** A SCIM `userName`, an OIDC user claim or a trusted identity header starting with `workload:` (any case) is refused, so only a verified workload credential can carry a workload subject.
- **Every mutation is audited** with actor `scim`, fail-closed like other privileged actions.

Limit: the gateway caches directory entries (`cacheTTL`, default 1m; `grace` 5m while `halo-server` is unreachable), so a deprovisioned user keeps their cohort at a gateway that long. With `halo-server` unreachable past `grace` and nothing cached, a deprovisioned user whose IdP token is still valid gets default routing under their own identity (fail open), not a refusal; set `failMode: closed` to refuse instead. Whether their IdP token is still accepted at the gateway is the IdP's decision.

## Bedrock credentials

For `kind: bedrock` upstreams `halo-proxy` signs with SigV4 using **its own** AWS identity (the AWS SDK default chain: env, SSO profile, EKS IRSA or Pod Identity, ECS task role, EC2 instance profile). The caller's `Authorization`, `x-api-key` and **every** client `x-amz*` / `x-amzn*` header are always dropped, even with `forwardAuth: true`, so only gateway-set headers enter the signature. Signing happens only for AWS endpoint hosts (suffix `.amazonaws.com`, `.amazonaws.com.cn` or `.api.aws`) or hosts listed in `signHosts`; a `kind: bedrock` upstream with a region on any other host gets a 502 `bad_upstream` rather than the gateway's signature. No credentials means a 502 `upstream_auth_error`; nothing is forwarded unsigned. The role should grant only `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream` on the models in policy. Setup: [stack-agnostic](/halos/concepts/stack-agnostic/#direct-bedrock-sigv4-in-halo-proxy).

## Verified installs

The release manifest carries, per harness, OS and architecture, an https URL with an exact size and a sha256 (binary) or sha512 integrity (npm tarball). `halod` refuses artifacts that do not match. The old install path (`installCommand`: `curl | bash`, `npm install -g` running lifecycle scripts as root) is disabled unless `allowShellInstall: true`, which logs a warning on every use. An artifact cannot replace `halod` itself.

## Gateway gates

Two per-ring policies enforce in the traffic path, which developers do not control ([ADR-0011](/halos/adr/0011-gateway-enforced-posture-and-version/); details in [delivery](/halos/concepts/delivery/#gateway-gates)):

- **`posture`.** The gateway asks `halo-server` (`GET /api/v1/gateway/posture`, gateway token or `--gateway-posture-token-file`, rate-limited) whether every enrolled device of the verified caller reported recently, without drift, on its ring's release. Reports are authenticated with the device token `halod` already holds; no new credential or crypto. It fails closed only on a verdict the server returned: an unreachable server leaves the last verdict in force for a grace window, then the request passes and is counted as unknown. An anonymous caller is unknown too.
- **`versionGate`.** The gateway parses the CLI version from the User-Agent and refuses one the ring does not pin. An unknown or missing User-Agent follows the same mode.

Both default to `warn` (log and count). In `enforce` they answer 403 with the reason and the fix (`halod status`). Neither reads a client `x-halo-*` header; `halo-kong`'s `x-halo-gate` upstream tag is stripped from the client first like every other `x-halo-*`.

## Root-side hardening in `halod`

`halod` runs as root and applies configuration delivered over the network, so it treats the signing key as *necessary but not sufficient*:

- **Path allowlist.** Files may be written only under each harness's admin config directories (see [delivery](/halos/concepts/delivery/)). `..`, relative paths, backslashes on unix and alternate-stream characters on Windows are refused. Stale-file removal uses the same allowlist.
- **Mode ceiling.** A manifest entry with a mode above 0644 is refused.
- **Ownership preflight.** Before it starts, `halod` verifies the config, public key, device-token file and state file, and every ancestor directory, are owned by root (or SYSTEM/Administrators on Windows), not writable by group or other, and contain no symlink planted by a non-root user. The device-token file must be mode 0600. On Windows only the owner SID is checked, not the DACL, so harden the directory.
- **Atomic apply.** Temp file, fsync, rename. On any failure before verification nothing on disk changes, and the last good release stays.
- **Bounds.** Release size (default 256 MiB), artifact size and https-only redirects are capped. A failed ring lookup falls back to the last known ring, never to "no ring".

## Identity at the gateway

The gateway verifies the caller's OIDC JWT against the IdP's discovery document and JWKS (cached, refetched on an unknown `kid`): `iss`, `aud`, `exp`, `nbf`, and an algorithm limited to RS256, ES256 or EdDSA (`none` and `HS*` are rejected). The ring, experiment and variant are derived from the verified user and groups. Failed verification returns 401 unless `allowAnonymous` is set, in which case the caller gets default routing and ring `unknown`, never an experiment.

`trusted_header` mode exists for gateways that authenticate for you. It honors the identity headers only when the TCP peer is inside `trustedProxyCIDRs`; with no CIDRs it fails closed with 503. Never use it without the CIDR pin, and only if the gateway overwrites the header and clients cannot reach `halo-proxy` directly.

## Workload credentials

Headless agents (GitHub Actions, GitLab CI, Buildkite, CircleCI, cloud workloads) get no provider API key. `halo ci token` sends the job's own OIDC token to `halo-server` `POST /api/v1/token/exchange` (RFC 8693) and receives a gateway credential ([ADR-0023](/halos/adr/0023-workload-identity-federation/), [guide](/halos/guides/ci-and-cloud-agents/)):

- **Subject token verified like an IdP token.** The issuer must be listed in policy `workloads.issuers`; discovery and JWKS (cached, refetched when no cached key verifies), `iss`, `aud`, `exp`, `nbf`, `iat` not in the future, and the RS256/ES256/EdDSA allowlist (`none` and `HS*` are rejected).
- **Rules pin the tenant.** A rule of that issuer must match every listed claim (exact or glob; `*` never crosses `/`). Public issuers sign tokens for every tenant, with any `aud` a job asks for, so each rule must also match one of the issuer's tenant claims exactly, or as `literal/*`: GitHub `repository_owner_id`, `repository_owner`, `repository` or `repository_id`; GitLab.com `namespace_id`, `namespace_path`, `project_id` or `project_path`; Buildkite `organization_id` or `organization_slug`; CircleCI `oidc.circleci.com/org-id`; Google `email` or `sub`; Entra ID `tid`. `ref: refs/heads/main` alone, or `repository_owner: acme*`, fails `halo validate`. Any other issuer must name its `tenantClaim`. For a known issuer `tenantClaim` may only narrow the choice to one of these claims; any other value (`ref`, `environment`) fails `halo validate` and is ignored at runtime, so it can never make `ref: refs/heads/main` a tenant pin. GitHub, GitLab.com and Buildkite rules that pin only renamable names (no `repository_owner_id`/`repository_id`, `namespace_id`/`project_id`, `organization_id`), and GitHub rules with no `environment` or `job_workflow_ref` (so `pull_request_target` runs on the base branch match), validate with a warning. The subject must start with `workload:`, so a workload never takes a human's id.
- **Enforced at runtime, not only by `halo validate`.** `halo-server` and both gateways run the security validation (workloads, units, delegation) on every policy load and refuse to activate a policy with an error there, keeping the last good one with an error log and a counter (`halo_server_policy_refused_total`, `halo_proxy_policy_refused_total`). A refused policy still removes workload rules on `halo-server`: the rules in effect become the last good policy's rules that the refused one still has unchanged, so an unrelated error cannot block the emergency removal of a compromised rule. Additions and changes are not applied; each such load is logged and counted (`halo_server_policy_tightened_total`), and the in-process controller sees the same policy. The exchange itself never matches a rule that pins no tenant (`halo_server_workload_rules_skipped`, a gauge set per load, counts any in effect). `halo release build` and `publish` refuse any invalid policy.
- **Single use.** Each subject token is exchanged once while valid (by `iss` + `jti`, or by its hash when the issuer sends no `jti`).
- **Rate limited without a shared-runner lockout.** Hosted CI runners and NATs put many tenants behind one IP, and any of them can mint a signed token for its own repository. So the exchange's per-IP budget counts only subject tokens that are malformed, name an unlisted issuer or fail the signature check; a signed token that matches no rule, is replayed, expired or for another audience costs nothing. A signed token is accepted even from a blocked IP, verified from cached discovery and keys only (a blocked IP never makes `halo-server` call the issuer); anything else from a blocked IP is 429.
- **Short-lived, dedicated key.** The credential is an EdDSA JWT (`typ: halo-workload+jwt`, `kind: workload`) signed with `--workload-key-file`, which is neither the release nor the kill-switch key. Default lifetime 15 minutes, never more than 1 hour; gateways reject it at `exp` with no leeway and refuse any lifetime over an hour.
- **Same gateway rules as humans.** Every inbound `x-halo-*` is still stripped and the ring comes from the credential's groups. Workloads get control routing and no shadow unless policy sets `workloads.experiments: true`.
- **Audited.** Every exchange appends `workload.token.exchange` (fail closed) with the rule, issuer and matched claims, never a token. A verified token that no rule matches, or a replay, appends `workload.token.denied`. Unverifiable input is logged, not audited.

Limit: the replay cache is per `halo-server` process, so with several replicas a token can be exchanged once per replica within its lifetime.

## Delegated agents

A subagent, background agent or A2A caller gets its own short-lived credential, minted from its parent's at `POST /api/v1/token/exchange` with an `actor_id` ([ADR-0024](/halos/adr/0024-agent-identity-and-delegation/), [guide](/halos/guides/agent-identity/)):

- **The subject stays the root principal.** The credential's `sub` and groups are the human's or workload's. Ring, toggles, posture and budgets are computed for the root, an agent of a deprovisioned user is refused at the gateway like the user, and delegated callers get no experiment unless `agents.experiments` (then exactly the root's arm).
- **RFC 8693 `act` chain.** The current actor is on top, prior actors nested. EdDSA with the workload key, `typ: halo-agent+jwt`. Unknown claims, a chain longer than five, a repeated agent (a cycle) or any edit under the signature are refused by the one verifier halo-server and both gateways share.
- **Scope only narrows.** The agent must be in `agents.actors`, the chain within the depth limit (default 2, lowered by profile and unit), and models within the parent's scope, `allowedModels` and the actor's models. An empty intersection is refused, never widened. A group the parent does not hold is refused, and narrowing groups is refused because it could move the agent's ring or budget. Lifetime is at most `maxTTLSeconds` and the parent's remaining lifetime.
- **Dead roots kill the chain.** A revoked session or a SCIM-deactivated root refuses the next exchange anywhere in the chain, and the next egress decision (the signed `auth_time` is compared with the session revocation epoch).
- **Re-checked per call.** The gateway refuses a chain any of whose agents was removed from policy or no longer admits the root's groups, a chain over the current `maxDepth` or the root's profile and unit `maxDepth`, a model outside the credential scope, `allowedModels` or the models of any actor in the chain, or a `deniedTools` tool. Tools are read from an explicit list of request shapes (Anthropic `tools[]` and `mcp_servers[]`, OpenAI Responses `tools[]`, Gemini `functionDeclarations` and built-in tool keys, Bedrock Converse `toolConfig.tools[]` and `additionalModelRequestFields`), keys matched ignoring case and underscores and across duplicate keys. A hosted tool counts by its type (`web_search_20250305`, `codeExecution`, `mcp:<server>`) and a deny entry matches it as a prefix. With `deniedTools` set, a body whose tools cannot be read (too deep, malformed, an unknown shape) is refused. `x-halo-actor` and `x-halo-actor-depth` are gateway-owned like every `x-halo-*`.
- **Audited.** `agent.token.exchange` and `agent.egress.allow` are fail closed: no credential and no allow without an audit record. `agent.token.denied` and `agent.egress.deny` (refusals, including a revoked or deprovisioned root and an unresolvable policy) record the chain, the root and the jti, best-effort; a failed append increments `halo_server_audit_append_errors_total`. Never a token. `actor_harness` and `actor_session` are self-asserted labels limited to `[A-Za-z0-9._:-]` (64 and 256 bytes), not controls.
- **Rate limited apart.** Delegation and egress have their own failed-authentication budget per client IP, separate from CI token exchange: a delegation request is dispatched before the CI budget is consulted, so CI failures never block it. Only bad, forged or unverifiable credentials spend it; policy refusals of an authenticated caller, and a parent or agent credential this server signed that has expired or whose root is gone, do not. At the exchange a parent this server signed passes even from a blocked IP.

Remote A2A agents are an allowlist (`agents.remote`) with a pinned AgentCard digest, an optional signing key or JWKS, skills, and the rings and units that may call each. `halo agents verify` fetches cards over https only, with no off-host or downgrade redirects, a size cap and a timeout, and refuses non-public destinations (checked on the dialed address). It never follows a card's `jku`. IPv6 transition ranges that embed an IPv4 address (NAT64, 6to4, Teredo, IPv4-compatible) are refused outright. Card digests reject invalid UTF-8 and lone surrogates, the card's fields are read by exact key, and text printed from a card has control and format characters escaped. Ring releases carry the pinned digests; `POST /api/v1/agents/egress` answers allow or deny for a verified Halos credential, audited.

Limits: delegated credentials are not individually revocable before `exp`. The gateway has no session revocation list: a revoked root's agent keeps calling models until the credential expires (at most `maxTTLSeconds`) or SCIM deprovisioning reaches the gateway's directory. The egress API is advisory until a proxy enforces it.

## Header spoofing

Clients can send any header. The gateway deletes every inbound `x-halo-*` (and the configured identity and groups headers once the subject is derived), then computes and sets the stamps. See [gateway headers](/halos/reference/gateway-headers/). This is exercised in the compose demo: a request claiming `x-halo-ring: ring3-ga` reaches the upstream with the ring derived from the token.

## Model allowlist fails closed

Only exact model-call paths are accepted (`/v1/messages`, `/v1/messages/count_tokens`, `/v1/responses`, Bedrock `/model/{id}/invoke*` and `converse*`). Any other path under those prefixes is 404, `/v1/messages/batches*` is 400, oversize or unreadable bodies are 413, and a model that is not a policy alias is 400 (`invalid_request_error`) with an error body in the caller's wire format. Nothing rejected is forwarded, and a rewrite failure is never forwarded un-rewritten.

## Guardrails

Default guardrails are Go code ([ADR-0007](/halos/adr/0007-guardrails-in-go-not-opa/)) run by `halo validate` and again at release build: no `bypassPermissions`, `disableBypass` required on every ring, reserved non-allowlisted override keys, reserved env prefixes, literal-secret detection, strict names. The release build then parses the rendered files and rejects `bypassPermissions` or `danger-full-access` in any value, as a backstop for adapter bugs and for `overrides`, which are merged after rendering. See [policy model](/halos/concepts/policy-model/#guardrails).

## Delegated units

Unit owners approve their own directory ([ADR-0018](/halos/adr/0018-org-hierarchy-and-delegated-policy/)), so `halo validate` treats anything a unit overlay adds that could run code or reroute traffic on members' machines as a loosening, reported at its field path: hooks (unless `delegation.allowHooks`), new env keys (unless listed in `delegation.envKeys`), and MCP servers that are not an exact `selfService.catalog` entry. Provider, base-URL, proxy, telemetry, CA-trust and runtime-injection env keys are refused even when listed, matched case-insensitively: `*_BASE_URL`, `*_API_KEY`, `ANTHROPIC_*`, `OPENAI_*`, `GEMINI_*`, `CLAUDE_CODE_*`, `AWS_*` (including `AWS_ENDPOINT_URL*`), `GOOGLE_*`, `CLOUD_ML_REGION`, `HTTP(S)_PROXY`, `ALL_PROXY`, `NO_PROXY`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `NODE_EXTRA_CA_CERTS`, `PATH`, `BASH_ENV`, `ENV`, `GIT_SSH_COMMAND`, `GIT_CONFIG_*`, `GIT_EXEC_PATH`, `npm_config_*`, `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `PERL5OPT`, `RUBYOPT`, `NODE_*`, `LD_*`, `DYLD_*`, `PYTHON*`; every `OTEL_*`; shell start-up and prompt hooks (`BASH_FUNC_*`, `PROMPT_COMMAND`, `SHELLOPTS`, `BASHOPTS`, `PS4`, `ZDOTDIR`, `HOME`, `XDG_CONFIG_HOME`); programs tools start (`PAGER`, `GIT_PAGER`, `MANPAGER`, `LESSOPEN`, `LESSCLOSE`, `EDITOR`, `VISUAL`, `GIT_EDITOR`); git (`GIT_SSH`, `GIT_ASKPASS`, `SSH_ASKPASS*`, `GIT_PROXY_COMMAND`, `GIT_TEMPLATE_DIR`, `GIT_SSL_NO_VERIFY`, `GIT_SSL_CAINFO`); compilers and runtimes (`GOFLAGS`, `RUSTC`, `RUSTC_*`, `CARGO_*`, `PERL5LIB`, `RUBYLIB`, `JDK_JAVA_OPTIONS`, `DOTNET_STARTUP_HOOKS`, `ELECTRON_RUN_AS_NODE`); and harness config dirs (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`). Adapters write every key Halos sets (gateway routing, model pins, telemetry) after the profile's env, so an env key never overrides them. `halo-server` and the gateways also refuse to activate a policy whose units or delegation fail validation (see [workload credentials](#workload-credentials)). Overlays cannot carry extensions (plugins, marketplaces). A top-level unit selects members from the whole org, so it may use `members.groups` only, and `halo units codeowners` gives its file to the root owners alone.

## Budget metering

`halo-proxy` charges a budget from the usage the provider reports at the end of a response. A 2xx model call is never free: if the body ends before its final usage is read (the client hangs up, the upstream cuts, the encoding cannot be decoded, no usage object), it charges a pessimistic estimate, counted as `estimated`. Output is estimated from the generated text in the stream's delta events (/ 4, at least a token per event), not from the SSE wire bytes, and capped at the request's max output tokens or `budgets.maxEstimatedOutputTokens` (default 128000). A request that makes the provider bill input its body does not carry is charged at least `budgets.serverStateInputTokens` (default 200000) of input: on OpenAI Responses `previous_response_id`, `conversation`, a stored `prompt` id, `background: true`, `input_file` by `file_id` or `file_url`, `input_image` by `file_id` or an http(s) URL, `item_reference`, and the `file_search`, `web_search*`, `mcp` and `code_interpreter` tools; on Anthropic (and Bedrock invoke) the server tools (`web_search`, `web_fetch`, `code_execution`, `tool_search`), `mcp_servers`, container uploads, and document or image sources of type `file` or `url`. Hidden reasoning is billed as output but never streamed, so when the request enables it (Responses `reasoning` other than effort `none`, Anthropic `thinking` or an `output_config` effort, Gemini `thinkingConfig`) the output estimate is at least the thinking budget, else the output cap. A background request answered with `usage: null` is charged the input floor plus the output cap. gzip and deflate responses are decompressed for the usage scan only; the client gets the upstream's bytes.

Limit: an `enforce` budget is checked before the call against what has been charged so far, and a response is charged when it ends, so one call can overshoot the limit by its own cost (including an estimate); the next call is refused.

## What Halos will not do

- Emit `bypassPermissions` or `danger-full-access`, including via `overrides` (overrides are an allowlist).
- Auto-promote a release, auto-merge a PR, or push to your main branch. The MCP server has no publish, retag or merge tool, and the only push it makes is a `halos/*` review branch behind a PR.
- Execute a shadow candidate's tool calls.
- Merge or auto-promote from the controller: it only opens PRs. Its one automatic action that changes live traffic is the kill switch, which only ever reverts to control.

## Limits

- Harness enforcement is only as strong as the harness. Where the [matrix](/halos/reference/harness-matrix/) says `halod` enforces, root can still stop `halod` or edit its files; on rings with `posture: enforce` that device then loses gateway access, and `versionGate: enforce` refuses CLIs off the pin ([gateway gates](#gateway-gates)).
- Posture is `halod`'s own report, not hardware attestation: root can read the device token and post a forged clean report. Posture is checked per user, not per request, so a user with a compliant laptop can use their credential from an unmanaged machine. The User-Agent is client-controlled: the version gate catches stale and unmanaged installs, not a forged header.
- The signing key is a single point of trust. There is no threshold signing. The kill-switch key is a second, narrower one.
- The audit log is tamper-evident, not tamper-proof, and tail truncation is undetectable on its own (see [Audit log](#audit-log)).
- The enrollment bootstrap (`curl -fsSL <server>/enroll.sh | sh -s -- <token>`) is itself a piped script whose integrity rests on TLS to your server. It pins the `halod` binary by sha256 and refuses to install without a pinned checksum.
- Shadow is single-turn only ([ADR-0004](/halos/adr/0004-shadow-single-turn-only/)).
- The `halo-kong` Go plugin runs as a separate process; treat its socket as part of the trust boundary.
- **UNVERIFIED:** the above was tested with unit tests, the compose demo, and the kind, real-CLI and Kong OSS UAT suites in CI, not against a real fleet, Kong Enterprise or Konnect, real AWS Bedrock, or a third-party penetration test.

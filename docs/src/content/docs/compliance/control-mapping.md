Halos is open-source software. It holds no SOC 2 report, no ISO/IEC 27001 certificate and no attestation of any kind, and nothing on this page says otherwise. **You are the party that gets audited.** This page lists the controls Halos helps you implement and the evidence it produces, so you can point an auditor at a file, a command or a log instead of a promise.

Read it with three limits in mind:

- A row says Halos can produce evidence for a criterion. It does not say that using Halos satisfies the criterion. Whether a control is designed and operating is the auditor's call, on your environment.
- No auditor or assessor has reviewed this mapping. It was written from the code and the ADRs. The security claims are held by the tests listed in the [security model](/halos/concepts/security-model/#tests-binding-each-claim); the rest of the evidence is only as good as how you deploy it.
- Halos has had no third-party penetration test ([SECURITY.md](https://github.com/dshakes/halos/blob/main/SECURITY.md), [threat model](/halos/reference/threat-model/)).

Companion pages: [data flow and PII inventory](/halos/compliance/data-flow-and-pii/) and [security overview](/halos/compliance/security-overview/).

## NIST SSDF and SLSA

Two different things are mapped here, and they should not be confused:

- **Consumer side.** Halos as the control you put around the agent software your developers install and the skills, plugins and hooks they load.
- **Producer side.** How the Halos project builds and releases itself.

SSDF numbering is NIST SP 800-218 v1.1.

| Practice | Consumer side (your fleet) | Producer side (Halos releases) |
|---|---|---|
| **PS.1** Protect all forms of code from unauthorized access and tampering | Policy repo plus signed releases; `halod` refuses anything that does not verify; path allowlist and ownership checks on what a release may write | Changes reach `main` by PR; the human merge gate depends on branch protection and `CODEOWNERS`, which are GitHub settings (UNVERIFIED here, see [security overview](/halos/compliance/security-overview/#sdlc)) |
| **PS.2** Provide a mechanism for verifying software release integrity | ed25519 release signature, signed ring pointers, hash-pinned artifacts | `checksums.txt` cosign keyless signature; image signatures; `install.sh` verifies; the `verify` job re-checks the published artifacts |
| **PS.3** Archive and protect each release; collect and share provenance | Releases are immutable and content-addressed; AI-BOM and SLSA provenance attach to each release as a signed referrer | GitHub releases keep archives, SBOMs and attestations; `actions/attest-build-provenance` in `release.yml` |
| **PW.4** Reuse existing, well-secured software; verify third-party components | Artifact pins, signatures (`requireSignatures`), static scan, MCP registry | Dependencies are in `go.mod`/`go.sum` and `web/package-lock.json`; `govulncheck` in CI; no automated dependency-update bot is configured in the repo |
| **PW.7** Review or analyze code | `halo validate` guardrails and the release backstop check what an agent is allowed to be configured to do | Required CI checks, agent review labels, human review (see [security overview](/halos/compliance/security-overview/#sdlc)); `golangci-lint` |
| **PW.8** Test executable code | Eval gates and experiments test a change on your tasks before promotion | `go test -race`, fuzzing, end-to-end and UAT suites |
| **PW.9** Configure software to have secure settings by default | Guardrails default on; `bypassPermissions` and `danger-full-access` are never emitted; `posture` and `versionGate` default to `warn` and DLP actions to `monitor`, so tightening is an explicit choice | `allowShellInstall: false`, anonymous gateway access off by default |
| **RV.1** Identify and confirm vulnerabilities on an ongoing basis | `versionGate` and rollouts for fast CLI upgrades | `govulncheck`, nightly fuzzing, weekly OpenSSF Scorecard run ([`scorecard.yml`](https://github.com/dshakes/halos/blob/main/.github/workflows/scorecard.yml)), private vulnerability reporting |
| **RV.2** Assess, prioritize and remediate vulnerabilities | Rollback and kill switch as the fast path | Disclosure process and targets in SECURITY.md |

SLSA (Build track, v1.0):

- **Halos releases.** Built on GitHub-hosted runners by GoReleaser. Archives get a build-provenance attestation (`actions/attest-build-provenance`), checked in CI with `gh attestation verify --signer-workflow`. **Halos does not claim a SLSA Build level.** The attestation and the `verify` job are the evidence; the level is a judgment you make from them.
- **Your agent releases.** `halo release build` writes an in-toto Statement v1 with a SLSA provenance v1 predicate whose `builder.id` is the `halo` binary and version (`internal/release/attest.go`). It records the policy commit, resolved artifacts and harness installs. The tool writes it about itself, on whatever machine runs it, so it is an input record, not isolated-build evidence. If you need a SLSA level for your policy releases, build them in a CI platform that produces its own attestation and treat Halos' provenance as additional detail.

## EU AI Act

Regulation (EU) 2024/1689. Read this section before the table:

- **Halos is not an AI system provider for the coding agents it manages.** The agents are vendors' products. Halos itself contains no model; the optional judge, `halo eval online` and `halo copilot` call a model you configure.
- **Risk classification is yours.** A general coding assistant is not in the high-risk categories of Annex III by default. Articles 12, 14, 19 and 26 attach to high-risk systems. If you use agent or ledger data to evaluate or monitor individual workers' performance or behavior, take legal advice: Annex III, point 4 (employment, workers management) may then apply to that use. Halos' ROI report compares randomized arms and is informational; the session ledger is per user.
- **General-purpose model obligations** (Articles 53 to 55) fall on model providers, not on Halos or on you as deployer. Transparency duties in Article 50 are not addressed by Halos.
- **UNVERIFIED:** article numbers are from the Regulation as adopted. Application dates and some provisions (Article 4 among them) were the subject of amendment proposals; check the current consolidated text before relying on any row.

| Provision | Applies to | What Halos provides | Evidence | Not covered |
|---|---|---|---|---|
| **Art. 4** AI literacy | Providers and deployers of any AI system, regardless of risk class | Nothing that trains people. Guardrail and gate messages tell a developer what was refused and why; the `halos-onboard` skill walks an operator through setup | None that counts as a literacy measure | The measures themselves: training, guidance, records of who completed it |
| **Art. 14** Human oversight | A design requirement on **providers** of high-risk systems | The agents' own oversight features belong to their vendors. What Halos adds is deployer-side: it never emits permission-bypass modes (invariant 1), promotion and merge are human (invariant 5), a signed kill switch and incident freeze can stop a change | Promotion PRs, approval entries, kill and freeze entries in the audit log | Whether the agent vendor's system meets Art. 14 |
| **Art. 26(2)** Assign human oversight to competent people | **Deployers** of high-risk systems | Named roles (`operator`, `approver`) and approver quorums with distinct groups and tickets give a place to record who holds the authority | Role mappings in policy; approvals in the audit log | Choosing the people, and their competence, training and authority |
| **Art. 12** Record-keeping (automatic event logging) | A design requirement on **providers** of high-risk systems | Not applicable to Halos as a product. Halos does not implement the agent's own event log | n/a | The agent vendor's logging |
| **Art. 19** Logs kept by providers (at least six months) | **Providers** of high-risk systems | Not applicable to Halos itself | n/a | n/a |
| **Art. 26(6)** Logs kept by deployers (at least six months, to the extent under their control) | **Deployers** of high-risk systems | Halos keeps governance records: hash-chained audit log, session ledger metadata (who, release, models, tools, tokens, cost, outcome), gateway metrics. Retention defaults are in the [inventory](/halos/compliance/data-flow-and-pii/#retention-defaults): the audit log is unbounded unless you prune it; the ledger copy in ClickHouse expires at 400 days | Audit log, ledger export, SIEM | **Halos does not log prompts or completions** (the ledger cannot hold prompt text; the gateway request log has no bodies). If your classification needs the system's input and output logs, they must come from the agent vendor or from your own capture. Reconcile the period with data protection law |
| **Art. 26(7)** Inform workers' representatives and affected workers before use at the workplace | **Deployers** who are employers, of high-risk systems | Not applicable | n/a | The notice, and works-council consultation under national law |

## What Halos does not cover

These stay with you, whatever the framework.

| Area | Why Halos cannot do it |
|---|---|
| Physical and environmental security (SOC 2 CC6.4, CC6.5; ISO 27001 Annex A 7.x) | Software |
| People: hiring, screening, training, disciplinary process (SOC 2 CC1; ISO 27001 Annex A 6.x) | Software |
| Risk assessment, ISMS governance, statement of applicability, management review | Process |
| Identity proofing, MFA, password policy, SAML | Halos speaks OIDC (console, gateway) and SCIM 2.0; the IdP does the rest. There is no SAML support |
| TLS termination, certificates, network segmentation | `halo-server`, `halo-proxy` and `halo-shadow` have no TLS listener. Terminate TLS at your ingress or load balancer |
| Endpoint protection, OS patching, disk encryption | Halos manages AI CLI configuration, not the machine |
| Backups and disaster recovery execution | Halos documents what to back up; you run and test it |
| Incident response plan, breach notification, legal reporting | Halos provides levers and a record |
| Vendor due diligence and contracts, including each model provider | Halos limits what can be reached, not whether you should |
| Data protection: legal basis, DPIA, records of processing, data subject requests, transfer mechanisms | See the [data flow and PII inventory](/halos/compliance/data-flow-and-pii/) for the facts you need |
| Retention enforcement where Halos has no default | Audit log, `halo_eval_results`, `halo_delivery_prs`, Postgres journal rows |
| Independent assurance | No third-party penetration test or code audit of Halos exists; FIPS 140-3: `_fips` builds use the Go Cryptographic Module v1.0.0; Halos itself is not validated |
| Policy-repo branch protection and review rules | GitHub settings; Halos supplies a CODEOWNERS template and `halo freeze check` |

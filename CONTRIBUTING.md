# Contributing to Halos

Thanks for helping. This page covers the loop for code, docs and ADRs.

## Ground rules

- Read [AGENTS.md](AGENTS.md) (invariants and package map), the [architecture](https://dshakes.github.io/halos/concepts/architecture/) and the policy model (`internal/policy/types.go`) first. The Go types are the source of truth for YAML field names.
- Any claim about Claude Code, Codex or Gemini CLI behavior in code or docs must cite a source, or be marked unverified.
- Load-bearing changes (new language, broken invariant, new trust boundary, schema break) need an ADR first: copy an existing file in `docs/adr/` (MADR format), number it, open a PR. `docs/adr/` is canonical; `npm run build` copies it into the site.
- Be kind: see the [Code of Conduct](CODE_OF_CONDUCT.md).

## Development setup

```bash
git clone https://github.com/dshakes/halos && cd halos
make build            # halo halod halo-shadow halo-server halo-proxy halo-kong into bin/
make test             # go test -race ./...
make lint             # golangci-lint run ./...
make vuln             # govulncheck
gofmt -l .            # must print nothing
```

Docs:

```bash
cd docs && npm ci && npm run dev           # http://localhost:4321/halos/
npm run build                               # must pass before you open a PR
```

- Every page needs a one-sentence `description:` in its frontmatter (search and link cards use it) and an entry in the sidebar in `docs/astro.config.mjs`; the build does not fail on an orphan, so check.
- Diagrams are SVG generated by `python3 assets/src/build.py` (light and dark pairs into `assets/` and `docs/public/diagrams/`); edit the Python, not the SVG. No Mermaid.
- CLI and policy reference pages are generated: `make docs-gen`, never edit `docs/src/content/docs/reference/{cli,policy}/` by hand.

## Pull requests

1. Branch from `main`; keep PRs focused.
   Before you push, run the same gate CI runs: `gofmt -l .` prints nothing, then
   `go build ./... && go vet ./... && go test -race ./...`, plus `cd docs && npm run build`
   if you touched `docs/`. Paste the output in the PR's "How I verified" section.
2. Add or update tests. Adapter changes need golden-file tests and a matching entry in `internal/release/check.go`; traffic-plane changes should be exercised with `deploy/compose`. Never hand-edit generated files (`deploy/integrations` configs are generated by `internal/gateway/adapters`; run `go test ./internal/gateway/adapters -update`).
3. Update docs and `CHANGELOG.md` (Unreleased section) for user-visible changes. A docs page must match the code: if they disagree, fix the docs or flag the bug. Label anything you did not run as **UNVERIFIED**.
4. Commits: imperative subject, sign off with `git commit -s` (Developer Certificate of Origin).
5. CI must be green. A maintainer merges; contributors do not self-merge.

### What runs on your PR

| Check | What it is | Required to merge |
|---|---|---|
| `test`, `lint`, `vuln`, `tidy`, `cross`, `e2e`, `docs`, `web` ([ci.yml](.github/workflows/ci.yml)) | `go test -race`, golangci-lint, govulncheck, `go mod tidy` drift, macOS/Windows builds, end-to-end tests on real binaries, docs and console builds | Expected green |
| `review` ([sdlc-review.yml](.github/workflows/sdlc-review.yml)) | compass SDLC review: a Claude agent reads the diff for correctness, security and the invariants in [AGENTS.md](AGENTS.md), and labels the PR `agent:needs-fix` or `agent:reviewed-clean` | Yes |
| `qa` ([sdlc-qa.yml](.github/workflows/sdlc-qa.yml)) | compass SDLC QA: runs the suite and tries the change the way a user would | Yes |
| `security` ([sdlc-security.yml](.github/workflows/sdlc-security.yml)) | compass SDLC security pass on trust boundaries, secrets and guardrails | Advisory |

Agent findings are suggestions with a label, not an auto-fix: address them or reply on the thread with why not. Agents never merge; a human does.

## Adding a harness adapter

Follow the [new harness adapter guide](https://dshakes.github.io/halos/guides/new-harness-adapter/). Every capability cell you claim must cite a vendor source in `internal/harness/FACTS.md`, and anything not run against the real CLI stays listed as unverified.

## Security issues

Do not file them publicly. See [SECURITY.md](SECURITY.md).

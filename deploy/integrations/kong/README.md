# Kong

Two ways, pick one:

1. **Route to halo-proxy** (`kong.yml`, works with Kong OSS/Enterprise/Konnect, no plugin server):
   Kong forwards `/v1/messages`, `/v1/responses`, `/model/` to `halo-proxy:8088`. halo-proxy verifies the
   caller's JWT itself, so Kong can sit before or after your auth gateway. Keep `retries: 0`,
   `response_buffering: false`, long `read_timeout`.
   - If a Kong auth plugin consumes/hides the `Authorization` header, halo-proxy has nothing to verify.
     Either enable forwarding of credentials (e.g. `hide_credentials: false`), or run halo-proxy with
     `identity.mode: trusted_header`, `identityHeader: <header your plugin sets>` and
     `trustedProxyCIDRs: [<Kong's addresses>]`. Never use trusted_header without the CIDR pin.
   - For "Kong -> halo-proxy -> existing auth gateway/provider" set halo-proxy `nextHop` accordingly.
2. **halo-kong plugin** (in-process Go plugin, see `deploy/compose/` for a working Dockerfile and
   `kong.yml`): `identity_mode: jwt` verifies the JWT in Kong; `trusted_header` needs
   `trusted_proxy_cidrs`. Config is generated by `internal/gateway/kong`.
   Do not put Kong in front of an auth gateway and trust `x-*-user` headers: they are client-controlled there.
   The generated config is hardened as follows (keep these if you hand-edit it):
   - **Exact regex routes** (`~/v1/messages$`, `~/v1/messages/count_tokens$`, `~/v1/responses$`,
     `~/v1/models$`, `~/model/[^/]+/(invoke|invoke-with-response-stream)$`): prefix routes would let
     `/v1/messages/batches` etc. reach the upstream without the model allowlist.
   - **`nginx_http_client_body_buffer_size = 32m`** (`KONG_NGINX_HTTP_CLIENT_BODY_BUFFER_SIZE=32m`).
     Kong's default (8k) spools most Claude Code first turns to disk; halo-kong then can't read the
     body and answers **413** instead of forwarding an un-inspected model.
   - Routes are **`https` only**; `kong.Options.AllowHTTP` adds `http` for local dev.
   - `shadow_token` is a Kong **vault reference**, `{vault://env/halo-shadow-token}` (Kong's env vault
     reads `HALO_SHADOW_TOKEN`: upper-cased, `-` -> `_`). A literal token is refused by the generator:
     it would sit in `kong.yml` and be returned by the Admin API. go-pdk plugin schemas can't mark a
     field `referenceable`, so Kong passes the reference through and halo-kong resolves
     `{vault://env/...}` itself. nginx strips the environment from its workers, so also set
     `KONG_NGINX_MAIN_ENV=HALO_SHADOW_TOKEN` (nginx `env` directive) or the plugin server sees an empty
     token and halo-shadow answers 401. Other vault backends are not resolved for Go plugins.

Checked: `docker run -e KONG_DATABASE=off kong:3.8 kong config parse kong.yml` -> "parse successful".
Not checked: live traffic through Kong to halo-proxy.

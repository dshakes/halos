# Integrations: halo-proxy in any stack

`cmd/halo-proxy` (see its README for modes a/b/c) runs unchanged in front of, behind, or instead of
your gateway. These are starting points, not turnkey deployments.

| Dir | Contents | Checked |
|---|---|---|
| `kong/` | decK route to halo-proxy; halo-kong plugin alternative | `kong config parse` (3.8, db-less) OK; traffic not run |
| `envoy/` | static bootstrap, cluster + no route timeout | `envoy --mode validate` (v1.32) OK; traffic not run |
| `nginx/` | `location` with buffering off | `nginx -t` (alpine) OK; traffic not run |
| `aws-api-gateway/` | HTTP API -> VPC link -> ALB -> halo-proxy | **UNVERIFIED** (not imported into AWS); read the limits section |
| `litellm/` | halo-proxy in front of LiteLLM, or LiteLLM as an upstream | **UNVERIFIED** |
| `providers/` | policy upstream + credential templates: Bedrock (orchestrator), Anthropic, Vertex, Azure Foundry, OpenAI-compatible | **UNVERIFIED** (no provider accounts) |

`kong/kong.yml`, `envoy/envoy.yaml`, `nginx/halo-proxy.conf`, `aws-api-gateway/openapi.yaml` are
generated by `internal/gateway/adapters`; edit the templates in
`internal/gateway/adapters/templates/` and run `go test ./internal/gateway/adapters -update`.

Only one path has been exercised end to end: halo-proxy running in its own compose demo
(`deploy/compose/docker-compose.halo-proxy.yml`). Nothing in the table above has been run against
real traffic.
